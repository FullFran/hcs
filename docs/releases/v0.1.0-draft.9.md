# HCS v0.1.0-draft.9

Specification release. Instance documents keep `"hcsVersion": "0.1"`. The SDK changes only its
version number.

HCS-0007 said the trust anchor arrives at enrollment and nothing about how a distribution
replaces a root key, revokes an online key, or what a host does with a signature it cannot count.
HagaHarness had to answer all of it on its own while preparing its first release. This draft
writes down the generic part, aligned with TUF's "Update the root role".

## Changes a host must make

- **Signatures a host cannot count are ignored, not refused** (new HCS-0007-R024, #95). A
  signature by a key the host does not hold, one that does not verify, or one by a key outside
  its window does not count toward the threshold and is never a reason to refuse the document.
  A host that refused key sets signed by an extra root breaks overlap signing. Both reference
  implementations already behaved this way.
- **A refused key set changes nothing** (HCS-0007-R026). The host keeps its accepted key set and
  state and goes on verifying envelopes with it.

## What changed

### Specification

- **HCS-0007 key lifecycle** (ADR 0039, Proposed, #95).
  - R024 (above); R025, a host never takes its trust anchor, or a root key, from a document it
    receives; R026 (above).
  - Section 5.3.1 (informative): online key rotation; revocation by publishing a higher key set
    version without the key, then re-signing the current envelope without raising `sequence`
    (the content digest excludes `signatures`); root replacement by overlap signing.
  - R027 to R029 (SHOULD, distribution): sign with the old and the new trust anchor during a root
    transition, and refuse to sign with fewer roots unless the operator asks; revoke by omission;
    keep conformance fixture roots, and any input a document or endpoint can set, out of a
    production trust anchor.
  - Open questions OQ-0007-8 (a TUF-style root chain), OQ-0007-9 (the running set after its
    signing key is revoked), OQ-0007-10 (keys limited to one `binding` member; one harness).

### Conformance

- 8 generated cases for R024 and R025, 2 host cases for R026. The DISTRO-1 profile gains R024
  to R029.
- 518 cases in total (508 in draft.8): 393 run by the reference runner, 125 at `host` level.
  159 requirements (153 in draft.8).
- Known: the DISTRO-1 profile does not list R022 and R023, as in earlier drafts.

### SDK

- Version 0.1.0-draft.9. No API change. `signing.verifyKeySet` and `signing.verifyEnvelope`
  pass the new cases unchanged.
- The SDK still requires Node 24 or later.
