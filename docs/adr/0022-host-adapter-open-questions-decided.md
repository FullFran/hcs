# ADR-0022: Six host adapter questions decided: standardise only what has two implementations

**Status:** Accepted (2026-11-06, decided by the maintainer)

## Context

HCS-0008 left open questions that the first host needs answered to build its materializer. The Linux Foundation reasoning applied throughout ([lf-fit-host-adapter.md](../research/lf-fit-host-adapter.md)) is that a project does not standardise what has only one implementation (README rules 1 and 3).

## Decisions

1. **No core `instructions` kind yet (OQ-0008-1).** Instructions stay an extension kind; AGENTS.md is the content convention as a SHOULD. Revisit when a second harness ships instruction packages. Why: one harness; AGENTS.md defines content but no install location ([agents-md.md](../standards/agents-md.md)).
2. **Unprojectable kinds are reported, not fatal (OQ-0008-5).** An engine that cannot project a contribution reports `unsupported_contribution`; the entry is not active on that engine; the generation switch is not failed or rolled back for that reason (HCS-0008-R017). `all-or-nothing` keeps governing the signed catalog and its resolution (HCS-0003, HCS-0007-R016). Why: which kinds an engine takes is a per-engine fact, not a defect of the signed set; failing the switch would let one engine's gap block every other entry. Other projection errors stay failures.
3. **No dedicated health-failure code (OQ-0008-4).** A failed or late health check reuses `plugin_failed` or `timeout`; health is reported as a state, `healthy`, `unhealthy` or `unknown` (HCS-0008-R018, SHOULD). Why: the most widely used mechanisms report a state, not an error code: Kubernetes pod conditions (`Ready` with `status` `True`/`False`/`Unknown` and a machine-readable `reason`), gRPC health (`SERVING`, `NOT_SERVING`, `UNKNOWN`), boot assessment (entry good or bad).
4. **No host adapter conformance profile yet (OQ-0008-6).** Open it when a second host exists. Why: a profile with one implementation describes that implementation, not a standard (README rule 3).
5. **Regenerating `requirements/requirements.json` is part of every spec change.** It is generated by `tools/extract_requirements.py` and checked for drift; `CONTRIBUTING.md` says so.
6. **Agent and command definitions stay per-engine extension kinds** outside the normative text (HCS-0008 appendix A); an engine that cannot take them reports them under HCS-0008-R004 and R017.

## Consequences

- HCS-0008 gains R017 (MUST, `projection` cases) and R018 (SHOULD, no cases); OQ-0008-1, -4, -5 and -6 close. OQ-0008-2 and -3 stay open.
- HCS-0007 gets a note under R016 that it governs the catalog, not per-engine projection.
- The reference projection excludes an unsupported entry from `selected` without emptying it.
- A distribution may send one catalog to hosts whose engines take different kinds; each host reports what it cannot take.
