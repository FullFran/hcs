# ADR-0033: Archive member safety is a MUST list and reports `package_invalid`

**Status:** Proposed

## Context

HCS-0001 section 3.4 says a package is an OCI layer tar applied to an empty directory, and R007 and R018 verify the bytes before unpacking. Neither says which tar members a host must refuse (OQ-0001-6, issue 22). A package whose digest matches is exactly what the publisher described, so a hostile or careless publisher can still ship a member that writes outside the package root or hides another one. A second independent consumer enforced a local rule and reported the result: it refuses absolute paths, `..` segments, backslashes, NULs, empty and duplicate paths, `.wh.` components, directories that carry data, and every member that is not a regular file or a directory. It also reported two gaps: exceeding its member or size limit, and a malformed tar, raised an untyped error.

## Decision

1. A host MUST refuse a package whose tar has (R019) a member with an empty path, an absolute path, a `..` segment, a NUL or a backslash in the path, or a component that starts with `.wh.`; (R020) a member that is neither a regular file nor a directory, or a directory that carries data; (R021) a path equal to an earlier member's path, or a path below a regular file member, in any order. Paths are compared after resolving `.` segments and removing a trailing `/`.
2. The host checks this after `size`, `contentHash` and, when declared, `contentId`, before writing any member to its final location, and leaves nothing of a refused package there (R022). R007 and R018 keep their `integrity_mismatch` errors and their order.
3. A tar that cannot be parsed, or whose unpacked size or member count exceeds a limit the host sets, is refused (R023). A host MAY set limits; HCS states no number, because one implementation's defaults (256 MiB, 10,000 members) are not enough evidence. When `contentId` is declared, a failed or over-limit decompression stays `integrity_mismatch` (R018 is unchanged).
4. Every refusal reports the new HCS-0006 code `package_invalid`, with `requirement` set to the violated HCS-0001 requirement. The member path goes in an extension member of `details` (HCS-0006 allows only extension members there, so HCS does not name one). Neither `message` nor `details` carries member content.
5. Conformance: the `integrity` level gains `input.unpack`, which runs the member check on the verified bytes; fixtures can set `maxMembers` and `maxUnpackedBytes`. The archives are generated byte by byte by `conformance/runner/gen_package_cases.py`, because a tar library will not write them.

## Why every link is refused

Refusing only links whose target leaves the root needs a resolver: a link target is a path that is itself resolved against members that may come later, rewritten by earlier links, or changed by the host's own handling of `..`. Each of those is a place to get the check wrong, and the usual tar extraction escapes (a symlink that a later member is written through) come from exactly that gap. A package is a bundle of skill and server files; it has no need for links, devices or FIFOs. A rule with no resolver is one a second implementation can check by reading one header byte. This also covers hard links, whose targets are named by path and can point at a member not yet written. The same reasoning excludes extended header records: this version does not read them, so a name or size they would override is not one the host can check. Members below a regular file and directories with data are in the list because the SDK can test them and a producer never needs them; refusing them means the tree the host builds is the tree the archive lists.

## Why a new code and not `integrity_mismatch`

`integrity_mismatch` means the bytes are not the ones described, and the recovery HCS-0001 implies is to try another location. Here the bytes are exactly what the publisher signed; another location returns the same archive. A caller that treats the two alike retries a package that cannot succeed, and an operator reading the error cannot tell a corrupted download from a publisher fault. The registry is closed (HCS-0006-R002) and the second consumer's local strings show the need for a typed error for malformed tar and limits as well, so one code covers the three conditions and `requirement` tells them apart.

## Prior art checked

- OCI image-spec v1.1.1 `layer.md`: a whiteout is an empty file whose name is `.wh.` plus the basename of the path to delete; `.wh..wh..opq` is the opaque whiteout; "it is not possible to create a filesystem which has a file or directory with a name beginning with `.wh.`"; implementations "MUST accept both" explicit and opaque forms; a changeset "MUST NOT include duplicate entries for file paths"; extracting a layer with hardlinks to files outside the layer "may fail". The spec has no rule for absolute paths, `..` traversal or links leaving the root. HCS applies one archive to an empty directory, so a whiteout has nothing to delete and no meaning; refusing it keeps a name that other tooling reads as a deletion from appearing in a package.
- node-tar (the library npm uses for package tarballs), README security notes: absolute paths are turned into relative paths under the target; paths that walk up outside the target are ignored with a warning; `Link` and `SymbolicLink` entries may not target locations outside the extraction folder; extraction through a symbolic link inside the target is not allowed; most of this is disabled by `preservePaths`. That tool repairs or skips a bad member and continues. HCS refuses the package instead: a host that quietly drops a member has unpacked a tree the publisher did not describe, and two hosts can drop different members. It also restricts links only by where they point, which is the resolver HCS avoids.

Both were read from the published documents (`layer.md` at tag v1.1.1 and the node-tar README); neither implementation's code was read.

## Consequences

- A package that contains a link, device, FIFO or extended header record is refused even where a host could extract it safely. Producers using `buildPackage` or any plain tar of regular files and directories are unaffected. A tar made with GNU tar long-name or pax records needs its names to fit the ustar `prefix`/`name` fields.
- A tar of a directory made with `tar -C dir .` has a `./` root member, which is an empty path under R019. Producers leave it out; `buildPackage` never writes one.
- The SDK reported these refusals as `integrity_mismatch` and a malformed tar or limit as an untyped error; it now reports `package_invalid` for all of them. A caller that branched on `integrity_mismatch` for an unsafe member must also handle `package_invalid`.
- Distributions that kept an `x-` code for this condition move to the registry code (HCS-0006 section 4.4).
- The conformance README and `docs/architecture.md` mention the closed code list and the integrity level; they need the new code and `input.unpack` (outside the writer's edit surface for this change).

## Alternatives rejected

- `integrity_mismatch` with a reason: see above.
- One requirement per refusal: a dozen separate requirements for rules that one sentence lists; the five requirements group rules by what they check (path, type, identity of paths, order, parse and limits) and each has its own valid and invalid cases.
- Normalizing or skipping bad members like node-tar: two hosts would build different trees from one package.
- A fixed unpack limit in HCS: no evidence for a number yet.

## Open

Whether extended header records should become readable (and then checked) is left to a producer that needs names longer than the ustar fields.
