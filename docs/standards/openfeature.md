## What it defines

A vendor-neutral feature-flag evaluation API (API, client, provider, hooks, evaluation context,
events). HCS does not use feature flags; it reuses how the specification is written, extracted
and tested.

## Key objects and fields

The process artifacts HCS copies:

- Requirement headings in Markdown: `#### Requirement 1.1.1`, followed by a blockquote holding
  one requirement with a bold BCP 14 keyword (for example `> The API ... **SHOULD** ...`).
- Conditions: `#### Condition 1.1.8` states when a set applies (for example a language feature);
  nested `Conditional Requirement` entries apply only under that condition.
- `specification.json` at the repo root: generated by `make` from the Markdown via
  `tools/specification_parser`; a `rules` array of objects with `id` (for example
  `"Requirement 1.1.1"`), `machine_id` (`requirement_1_1_1`), `content`, `RFC 2119 keyword`, and
  `children`. At v0.9.0 it lists 107 `Requirement`, 28 `Condition` and 37 `Conditional` ids.
- Document statuses per section: `Experimental` (breaking changes allowed in minor versions),
  `Hardening` (breaking changes need TSC consensus, may still land in minor versions), `Stable`
  (breaking changes only with a major version). No explicit status means `Experimental`.
- Gherkin suites in `specification/assets/gherkin/` (`evaluation.feature`,
  `evaluation_v2.feature`, `hooks.feature`, `contextMerging.feature`, `metadata.feature`, with
  `test-flags.json`) that SDKs run as shared conformance tests; a provider TCK is tagged
  separately (`specification/assets/provider-tck/v0.1.0`, 2026-10-16).
- Style rules: one sentence per line, imperative mood, entities in backticks, string literals in
  backticks plus quotes.

## Extension points

Not relevant as a dependency. As a process: new sections enter as `Experimental` and graduate;
conditional requirements scope language- or runtime-specific rules without forking the spec.

## Where HCS references it instead of redefining

- HCS-0000 conventions adopt the pattern: requirement IDs `HCS-NNNN-R<n>` (or section-numbered)
  as Markdown headings with one BCP 14 keyword each, and a generated `requirements.json` with the
  same fields as `specification.json`; HCS cites OpenFeature as precedent and does not claim the
  format as novel.
- HCS-0000 adopts the three statuses (`Experimental`, `Hardening`, `Stable`) with OpenFeature's
  breaking-change rules, and the default-to-Experimental rule for unmarked sections.
- CORE-0, TOOLS-1, AGENT-1, ISOLATION-1, DISTRO-1 conformance cases reference requirement
  `machine_id`s, so the runner report can show coverage per MUST (README rule 3).
- Shared, language-neutral fixtures (Gherkin or JSON fixtures) follow OpenFeature's model of one
  suite run by every implementation; HCS defines its own fixtures and runner.
- HCS MUST NOT depend on OpenFeature APIs or flag semantics.

## Pitfalls for HCS

- OpenFeature's parser keys on heading text; HCS needs a stable ID that survives renumbering
  (do not reuse a retired ID).
- `machine_id` derived from section numbers changes when sections move; HCS should assign IDs
  explicitly rather than derive them from position.
- Statuses are per section in prose; HCS should also put the status in the generated JSON so the
  runner can treat Experimental failures as non-blocking.
- "0.x with Stable sections" is confusing to readers; HCS should state how document status and
  HCS release version interact.
